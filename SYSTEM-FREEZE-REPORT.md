### Three defects found and fixed while getting this to run

1. **The two research gates disagreed.** `evaluation-runner.js` had been
   refined to block only what a given test set would actually contaminate;
   `database_connector.assert_research_ready()` still refused on *any*
   synthetic row anywhere. So the harness generated all 66 results and the
   scorer then refused to score them. Aligned at the same semantics, with the
   strict scope kept as the default so model training is unaffected.

2. **The judge was never wired up.** The scorer called `evaluate()` with
   metrics only and printed a note asking someone to configure a judge. RAGAS
   does not read `eval_run.judge_model` — with no `llm=` it builds a
   `ChatOpenAI` and dies on a missing `OPENAI_API_KEY`. The run therefore
   *recorded* a Llama judge while the scorer was reaching for GPT. **No RAGAS
   score had ever been produced in this project.** The judge is now built from
   the model name stored on the run.

3. **The recorded judge did not exist.** `llama-3.3-70b-versatile` returns
   404 on this Groq account. The runner accepted it, spent 66 completions, and
   only failed at scoring. `evaluation-runner.js` now asks Groq for its model
   list and refuses an unavailable judge before generating anything.

### The judge, and an honest limitation

This Groq account offers 13 models. Selecting a judge that is both usable and
distinct from the generator narrowed to one:

| Candidate | Verdict |
|---|---|
| `llama-3.3-70b-versatile` | 404 — not available on this account |
| `qwen/qwen3.6-27b` | emits `<think>` reasoning inline; RAGAS 0.1.9 cannot parse it as JSON |
| `allam-2-7b` | 7B-class, too weak for claim decomposition (audit F-05) |
| `groq/compound`, `-mini` | agentic systems, not deterministic judges |
| **`openai/gpt-oss-20b`** | **clean JSON, reasoning on a separate field** |

`judge_model != groq_model_id` is satisfied. **Limitation to state in Chapter
4:** the judge is the same model *family* as the generator (gpt-oss 20B vs
120B). A fully independent judge was not available on this account in a form
RAGAS can parse. The reasoning is recorded on `eval_run.notes`.

### Scoring is BLOCKED by the free-tier daily token cap

**No RAGAS score was produced.** Not a bug this time — a quota wall, measured
rather than guessed:

```
Rate limit reached for openai/gpt-oss-20b ... service tier `on_demand`
on tokens per day (TPD): Limit 200000, Used 199429, Requested 1433
```

| | |
|---|---|
| Evaluations needed | 4 metrics x 66 rows = **264** |
| Measured cost | **~4,069 tokens each** (199,400 tokens bought ~49 evaluations) |
| Total required | **~1.07 million tokens** |
| Free-tier allowance | **200,000 tokens per day**, rolling 24 h |
| Therefore | **~5.4 days** of free quota for one complete run |

Per-minute limits are not the obstacle — those are merely slow (8,000 TPM
gives ~4 evaluations/minute). The daily cap is a hard stop. Concurrency
cannot help: `max_workers=16` produced 25 minutes of pure backoff, and
`max_workers=1` was worse at 130 s/item. 4 is the best of the three.

Today's allowance is spent. The run reached **33 of 264** before stopping.

### What was fixed so a day's quota is never wasted again

The scorer was all-or-nothing: four metrics in one `evaluate()` call, written
only at the very end. So the day's 200,000 tokens bought 33 evaluations and
**zero** durable results. It now scores **one metric at a time and persists
each as it finishes**, with `--metrics` to resume:

```bash
python machine-learning/evaluate_rag_quality.py --run <id> --metrics context_precision
```

One metric is 66 evaluations ~= 270,000 tokens — still above a single day's
allowance, but partial results now survive, and the summary is read back from
the database so metrics scored on different days combine into one table.

A second latent bug was fixed alongside it: a NaN score (what
`raise_exceptions=False` produces on a failed evaluation) would have been
inserted straight into a column CHECKed to be between 0 and 1. Every
comparison against NaN is false, so the constraint would reject it — or a NaN
would be averaged as if it were a measurement. Unscored rows now store NULL,
which is what they actually are.

### Three ways forward — your call

| Option | Cost | Time to a complete RAGAS table |
|---|---|---|
| **Spread across days on the free tier** | none | ~5-6 days, one metric at a time |
| **Upgrade Groq to Dev tier** | paid | under an hour |
| **Use a non-Groq judge** (OpenAI/Anthropic key) | paid | under an hour, **and it removes the limitation below** |

The third option is worth noting beyond speed: it would also fix the fact that
the judge currently shares a model family with the generator, turning a
documented weakness into a clean claim of judge independence.

**Nothing about the generation run needs redoing under any option.** All 66
`eval_result` rows — with verbatim contexts, fused prompts, answers and
component latencies — are intact and were produced before the quota ran out.
Scoring reads from them.

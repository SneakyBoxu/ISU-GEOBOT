# ISU-GeoBot

A web-based campus navigation assistant integrating an **Enhanced RAG** architecture
— retrieval-augmented generation with a Random Forest availability classifier
embedded in the pipeline — for the Isabela State University Echague Main Campus.

Undergraduate thesis, BSCS (Data Mining Track), College of Computing Studies, ICT.
**Michael Allan Almario · Christian Paul Simbulan**

> **Research prototype.** No model has been trained, no evaluation has been run,
> and no results have been published. Everything in this repository is
> infrastructure for producing those results honestly — not the results.

## Architecture

```
React 18 SPA  ──►  Node 20 / Express 4  ──►  Python 3.11 / Flask
  Leaflet map        router · presence           Random Forest
  assistant          MASKING BOUNDARY            all-MiniLM-L6-v2
  /guard /validate   context fusion
                          │
                          ├──►  Supabase (PostgreSQL + pgvector)
                          └──►  Groq · Llama 3.1 8B · temperature 0
```

### Four invariants

Everything else is negotiable. These are not.

0. **A campus location is never in one place only.** Coordinates drive the map
   and a generated place-card drives retrieval; both are written together, so
   the map and the assistant cannot disagree about where something is.
1. **One pipeline, one mode flag.** Routing and retrieval are identical in the
   `standard` and `enhanced` arms. The only difference is whether Context Fusion
   appends the masked status block. Any other divergence confounds the thesis's
   primary evaluation.
2. **Only a three-value enum crosses the masking boundary.** Anything else is a
   hard error, never a fallback.
3. **No availability answer reaches the client without passing the egress
   filter.** Masking sanitises the model's input; the filter is what constrains
   its output.
4. **The evaluation harness refuses to run on synthetic data.**

## Run it right now (no accounts, no keys, no data)

```bash
cd server && npm install && npm run dev     # terminal 1
cd web    && npm install && npm run dev     # terminal 2
```

Open **http://localhost:5173**. `server/.env` ships with `DEMO_MODE=true`, which
swaps Supabase, Groq and the Python service for local stand-ins so the whole
application runs standalone.

Demo accounts, all with password `demo`: `student@demo.local`,
`faculty@demo.local`, `guard@demo.local`, `admin@demo.local`.

**What is real in demo mode:** the query router, tri-state presence resolution
and the deterministic override, the entire status masking boundary including the
egress filter, Context Fusion, both pipeline arms, and retrieval by cosine
similarity.

**What is a stand-in — and can never be reported:** availability comes from a
deterministic schedule lookup rather than a trained Random Forest; replies are
composed from templates rather than generated by Llama 3.1 8B; embeddings are
hashed lexical overlap rather than all-MiniLM-L6-v2; all data is placeholder.
An amber banner states this on every screen and the evaluation harness refuses
to run.

Step-by-step instructions for connecting the real services and data are in
[SETUP_STEPS.md](SETUP_STEPS.md).

## Full setup

### 1. Database

Run against your Supabase project, in order:

```bash
psql "$DATABASE_URL" -f db/schema.sql -f db/functions.sql -f db/policies.sql
```

Then verify RLS before doing anything else:

```bash
psql "$DATABASE_URL" -c "select * from geobot.rls_audit();"
```

Expected: `rls_enabled` and `rls_forced` true everywhere, `anon_readable` true
for `availability_status` **only**. Any other `true` in that column is a data
leak. Screenshot this for the defense.

Optional development data — every row is marked synthetic:

```bash
psql "$DATABASE_URL" -f db/seed/001_demo_data.sql
```

### 2. ML service

```bash
cd ml && pip install -r requirements.txt && cp .env.example .env && python app.py
```

Serves `/predict`, `/embed`, `/embed/batch`, `/tokenize/count`, `/model/info`,
`/healthz` on `127.0.0.1:5001`. **Never expose this publicly.**

### 3. Ingestion

```bash
python ingest.py --place-cards --origin synthetic
python ingest.py --path ./data/documents --origin real
```

Chunks are measured with the model's own tokenizer and capped at 220 word-pieces,
because all-MiniLM-L6-v2 truncates at 256 silently.

### 4. API

```bash
cd server && npm install && cp .env.example .env && npm run dev
```

### 5. Web

```bash
cd web && npm install && cp .env.example .env && npm run dev
```

Routes: `/` landing · `/app` map + assistant · `/guard` presence dashboard ·
`/validate` faculty portal · `/admin` campus location manager.

### Roles

| Role | Adds |
|---|---|
| anonymous | map, navigation, institutional questions |
| student | faculty availability queries |
| faculty | control over their own availability disclosure |
| validator | the functional-validation checklist |
| guard | presence logging |
| admin | campus location management |
| researcher | evaluation runs |

Availability requires an account by design: masking protects the granularity of
one answer but not the volume of them, and an anonymous availability endpoint
can be polled into a presence timeline. Faculty can pause their own disclosure
at any time — enforced before the classifier runs, so the estimate is never
computed rather than computed and withheld.

## Verifying the privacy boundary

```bash
cd server && npm test
```

27 adversarial tests covering allowlist projection, intermediate purge, override
precedence, the location-leak egress filter, and the response DTO allowlist.

This suite **is** the evidence that the Status Masking Protocol works. The
thesis plans no security audit of it; §3.5.3 presents illustrative code and
stops. If a panelist asks how you know masking holds, the answer is this suite
and its output — not the code listing.

## Evaluation

```bash
node server/src/services/evalRunner.js --label "run-01" --judge <judge-model>
python ml/score_ragas.py --run <eval_run_id>
```

Both arms run interleaved in one session, because Groq latency varies by minute
and is the dominant term in Response Time. The judge model must differ from the
generator; the database enforces it.

Random Forest and its comparison floor:

```bash
python ml/train_rf.py    --semester 2025-2026-1 --start <d> --end <d> --split time_based
python ml/baseline_rule.py --semester 2025-2026-1 --start <d> --end <d>
```

`baseline_rule.py` is the deterministic schedule lookup. The thesis claims
feature-importance analysis validates "the necessity of the machine learning
approach over a simple rule-based alternative" — it cannot; feature importance
is an intra-model diagnostic. Running the baseline is what supports the claim.
Either outcome is publishable, and you want to know which one before the panel
does.

## Research integrity

The following are **never** fabricated, placeholdered, or seeded: model accuracy,
RAGAS scores, response-time comparisons, faculty validation results, and research
conclusions. UI metric cards render an empty state until a real run exists.

Development data is separated by enforcement, not convention: every research
table carries `data_origin`, and `corpus_is_research_ready()` makes *"could
synthetic data have contaminated your results?"* a one-query answer.

**Still blocking a reportable result:** obtain a real sample of ISU attendance
data and confirm its time granularity. If it is a daily sign-in sheet rather
than intraday punches, intra-day availability labels cannot be derived without
imputing them from the schedule — which would make the classifier circular. See
[docs/OPEN_DECISIONS.md](docs/OPEN_DECISIONS.md) item 1.
